# Broker CMS v2

Источник истины для контента, дизайна и клиентской конфигурации сайтов брокерской платформы. Потребители выдачи: маркетинговый сайт, личный кабинет, торговый терминал.

> **Документация проекта — в [`docs/`](docs/README.md).** Это волт Obsidian: решения (ADR), задачи, баги, хвосты, открытые вопросы, журнал работ. Открывать как хранилище: `Открыть папку как хранилище` → `Broker_CMS/docs`.

## Быстрый старт

```bash
pnpm install
docker compose -f docker-compose.dev.yml up -d   # Postgres, Redis, RabbitMQ, MinIO
cp .env.example .env                              # значения уже совпадают с compose
pnpm run migrate                                  # применить миграции
pnpm run verify                                   # линтер + формат + типы + тесты
```

`pnpm run verify` прогоняет ровно то же, что и CI. Если он зелёный локально — он зелёный в CI.

Инфраструктура живёт в Docker, приложение запускается на машине: так цикл «правка → тест» не проходит через сборку образа. Порты смещены относительно стандартных (Postgres `5433`, Redis `6380`, RabbitMQ `5673`) — на машине может стоять своё.

Порт самого приложения — `3001` — не смещён, и на общей машине разработки его уже занимает dev-сервер витрины: `pnpm run dev` падает с `EADDRINUSE`. За кем закреплён порт, решает штаб — [`Q-009`](<docs/07-Вопросы/Q-009 — Порт 3001 занят соседней командой.md>). До решения помогает `npx next dev -p 3011`.

После `next dev` рабочее дерево оказывается грязным: фреймворк переписывает `next-env.d.ts` своим форматированием, и `format:check` краснеет ([`DEBT-012`](<docs/06-Хвосты/DEBT-012 — next dev переписывает next-env.d.ts и ломает format-check.md>)). Лечится `git checkout -- next-env.d.ts`.

**Схема БД меняется только миграциями**, dev-push отключён на любой базе, включая локальную. Подробнее — [`docs/02-Спецификация/Конвенции разработки.md`](docs/02-Спецификация/Конвенции%20разработки.md).

## Структура

```
src/
├── contracts/        JSON Schema выдачи, типы, эталонные фикстуры — канон контракта
├── modules/
│   ├── stream/       часть 1: новости, видео, промо, обучение, статус
│   ├── design/       часть 2: токены, блоки, страницы, навигация, SEO
│   ├── delivery/     часть 3: API, релизы, кеш, события, ключи
│   └── trading/      часть 4: тема терминала, инструменты, вотчлисты, кабинет
└── platform/         тенанты, наследование, доступ, воркфлоу, аудит, медиа, планировщик
```

### Правило границ

Модуль не импортирует внутренности другого модуля — только его публичный интерфейс (`index.ts`).

```ts
import { MODULE_NAME } from '@/modules/design' // можно
import { tokens } from '@/modules/design/internal/tokens' // падает в CI
```

Направление зависимостей:

```
modules/{stream, design, trading}  →  platform
modules/delivery                   →  modules/*, platform, contracts
platform                           →  (ни от чего)
```

Домены не знают, что их данные кто-то отдаёт наружу. Это условие, при котором `delivery` позже выделяется в отдельный сервис без переписывания.

Правило исполняемое, а не бумажное: нарушение ловится линтером, а сами правила покрыты тестами в `src/platform/architecture.test.ts`.

## Конфигурация

Все переменные обязательны, кроме `LOG_LEVEL`. Отсутствие **или пустое значение** любой из них означает отказ со списком всех проблем разом.

> [!warning] Для CLI это так, для HTTP-сервера пока нет
> `payload migrate` и прочие команды CLI при неполном окружении падают с кодом `1` до обращения к базе. А `next dev` поднимается, занимает порт и отдаёт `500` на первом запросе: `bootstrapEnv()` написан, но не подключён к точке входа. Дефект открыт — [`BUG-009`](<docs/05-Баги/BUG-009 — Сервис поднимается при неполном окружении.md>).

`process.env` читается ровно в одном файле — `src/platform/config/env.ts`. Везде остальном — `getEnv()`. Запрет принуждается линтером.

Полный перечень переменных с пояснениями — [`.env.example`](.env.example).

### Фоновые процессы

Три воркера, каждый запускается отдельно и ни один не обязателен для работы админки:

```bash
pnpm run worker:outbox     # публикация событий в шину
pnpm run worker:schedule   # переходы публикации потока по времени
pnpm run worker:mds        # снимок вселенной MDS раз в 5 минут
```

`worker:mds` — единственное место, откуда CMS обращается к MDS (ТЗ 4.2). Пока он не работал ни разу, снимка вселенной нет, и включение любого инструмента в карточку доступа требует осознанного подтверждения: проверить котируемость нечем. Это не поломка, а честное «неизвестно» — см. [`ADR-0030`](<docs/03-Решения/ADR-0030 — Разрешённые инструменты выбираются из вселенной MDS.md>).

## Работа с документацией

Документация обновляется **вместе с изменением**, а не после. Изменение без записи не считается сделанным.

После каждого изменения: статус задачи и лог · ADR на каждое решение с альтернативами · `DEBT` в момент, когда хвост оставляется, плюс `// TODO(DEBT-XXX)` в коде · `BUG` в момент обнаружения · запись в журнал в конце сессии.
