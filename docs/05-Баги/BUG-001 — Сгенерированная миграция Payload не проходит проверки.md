# BUG-001 — Сгенерированная миграция Payload не проходит проверки

> [!bug] Карточка
> **Статус:** 🟢 fixed `2026-07-30` · **Приоритет:** p1
> **Где:** `payload migrate:create` → `src/migrations/*.ts`
> **Не наш код:** дефект в шаблоне генератора Payload, проявляется на наших настройках

## Симптом

Первый же `payload migrate` падает, не дойдя до подключения к БД:

```
SyntaxError: The requested module '@payloadcms/db-postgres'
does not provide an export named 'MigrateDownArgs'
```

Следом, при попытке прогнать проверки, — четыре ошибки типов и линтера в том же файле:

```
error TS6133: 'payload' is declared but its value is never read.
error TS6133: 'req' is declared but its value is never read.
```

## Воспроизведение

1. `pnpm run migrate:create init_tenancy`
2. `pnpm run migrate` → падает
3. `pnpm run verify` → падает

**Окружение:** Payload 3.86.0, Node 24.18, tsx (загрузчик Payload по умолчанию), Windows.
**Частота:** каждый раз, на любой новой миграции.

## Причина

Две независимые, обе — следствие того, что генератор Payload рассчитан на менее строгие настройки проекта.

**1. Импорт типов как значений.** Шаблон генерирует:

```ts
import { MigrateUpArgs, MigrateDownArgs, sql } from '@payloadcms/db-postgres'
```

`MigrateUpArgs` и `MigrateDownArgs` — только типы. В обычном проекте esbuild вычищает их из импорта, потому что после стирания аннотаций они не используются. Но у нас в `tsconfig.json` включён **`verbatimModuleSyntax: true`**, и это меняет поведение принципиально: флаг требует сохранять импорты дословно. tsx читает наш `tsconfig`, сохраняет строку как есть, а в рантайме Node ищет в пакете экспорт `MigrateDownArgs` — которого не существует.

> [!note] Ложный след
> Сначала я решил, что виновато нативное стирание типов Node 24, и запустил CLI с `--no-experimental-strip-types`. Ошибка не изменилась — что и указало на настоящую причину: дело не в загрузчике, а в нашем собственном `verbatimModuleSyntax`.

**2. Неиспользуемые параметры.** Шаблон всегда деструктурирует `{ db, payload, req }`, хотя типовая миграция использует только `db`. У нас включены `noUnusedParameters` и правило линтера — оба отклоняют такое.

Обе настройки менять не нужно: они полезны и работают правильно. Несовместим шаблон.

## Исправление

`scripts/normalize-migrations.mjs` приводит сгенерированные файлы к правилам проекта: разделяет импорт на значение и тип, убирает неиспользуемые параметры. Скрипт идемпотентен и встроен в `pnpm run migrate:create`, поэтому вручную ничего делать не нужно.

## Урок

Пока писал скрипт, первая версия использовала регулярное выражение с якорями `^…$`. На файле с BOM оно не совпало — и скрипт **отчитался об успехе, ничего не исправив**. Это опаснее самой ошибки: молчаливый «успех» проверяемого шага. Якоря убраны, поведение проверено на файле с BOM и CRLF.

## Регресс-тест

Отдельного автотеста нет: поломка обнаруживается самим `pnpm run verify`, который прогоняется в CI на каждой миграции. Сгенерированный файл, не приведённый к правилам, роняет типы и линтер — то есть регресс невозможно не заметить.

> [!warning] Что проверить при обновлении Payload
> Если Payload поправит шаблон генератора, скрипт станет безвредным (он идемпотентен), но если шаблон **изменится иначе** — например, появится новый параметр — скрипт перестанет совпадать и снова придётся править вручную. Ревизия при мажорном обновлении Payload.
