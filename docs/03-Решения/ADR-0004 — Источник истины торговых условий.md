# ADR-0004 — Источник истины торговых условий

> [!success] Статус: ✅ accepted — принято заказчиком 2026-07-28
> Ответ на блокер [[Q-003]]. Заказчик выбрал «торговое ядро + обязательная сверка».
>
> ⚠️ Решение принято **при непроверенной предпосылке**: наличие у торгового ядра API с актуальными значениями плеча, спреда, swap-free и лота не подтверждено. Проверка вынесена в [[TASK-007]] как зависимость M4.

## Контекст

ТЗ (4.3) требует хранить витринные торговые параметры — плечо, спред «от», swap-free, размер лота — с явным указанием источника истины, и предупреждает:

> Расхождение витрины и реальных условий — прямой регуляторный риск.

Вариантов два: источник истины — CMS либо торговое ядро. Выбор определяет не объём работ, а **где находится ответственность за то, что клиент увидел цифру, которой не существует в реальности**.

## Решение

**Источник истины — торговое ядро. CMS хранит только маркетинговую подачу и обязана доказывать её соответствие ядру.**

Каждый витринный торговый параметр хранится не как число, а как запись:

```
{
  value,            // то, что видит клиент
  sourceRef,        // ссылка на параметр в ядре (символ/группа/счёт)
  rule,             // как value выводится из источника: equals | min_over_window | rounded_down
  tolerance,        // допустимое расхождение, для агрегатов
  verifiedAt,       // когда сверка последний раз прошла успешно
  status            // ok | stale | mismatch
}
```

Механика, обязательная к реализации на M4:

1. **Воркер сверки** периодически сравнивает `value` с ядром по правилу `rule` в пределах `tolerance`.
2. **`mismatch` → алерт** (Sentry + метрика Prometheus) и пометка записи. Расхождение — инцидент, а не запись в лог.
3. **Сборка релиза отклоняется**, если у публикуемого сайта есть параметр в статусе `mismatch`, либо `verifiedAt` старше заданного порога (`stale`). Это применение принципа fail-closed к торговой витрине.
4. **Свободный ввод числа запрещён.** Параметр без `sourceRef` не сохраняется. Витрина не может «обогнать» ядро.

> [!warning] Нюанс, который нельзя упустить
> «Спред от 0.0» — не равенство, а **агрегат по окну**: минимум за период по группе инструментов. Сверка «равно» тут даст ложные срабатывания, а сверка «примерно» — пропустит реальное расхождение. Поэтому `rule` и `tolerance` — обязательные поля, а не опциональные: для каждого параметра явно определено, что именно считается совпадением.

## Альтернативы

- **Источник истины — CMS.**
  Отвергнуто. Требует: воркфлоу с аппрувом risk-отдела на каждое изменение, юридической ответственности CMS за торговые параметры, и главное — создаёт второй источник, который **гарантированно** разойдётся с ядром, потому что ядро меняет условия оперативно, а CMS — через релиз. Расхождение будет не аварией, а нормальным режимом работы.
- **Гибрид: часть параметров в CMS, часть в ядре.**
  Отвергнуто: невозможно объяснить регулятору и редактору, какая цифра откуда. Смешанная модель — это отсутствие модели.
- **Витрина без сверки, «редактор следит сам».**
  Отвергнуто прямо ТЗ: механизм сверки и алерт названы обязательными.

## Последствия

- ✅ CMS перестаёт быть носителем регуляторного риска по торговым условиям — она носитель подачи.
- ✅ Расхождение обнаруживается автоматически и блокирует публикацию, а не всплывает в жалобе клиента.
- ✅ На вопрос «откуда эта цифра» есть машинный ответ: `sourceRef` + `verifiedAt`.
- ❌ Появляется жёсткая зависимость от торгового ядра: нужен API, отдающий актуальные параметры. **Если такого API нет — это блокер этапа M4**, а не задача CMS. Требует подтверждения от владельцев ядра.
- ❌ Редактор теряет возможность быстро «поправить цифру на лендинге». Это намеренно.
- ❌ Недоступность ядра переводит параметры в `stale` и со временем блокирует релизы — нужен явный порог и процедура ручного подтверждения с записью в аудит.
- 🔁 Пересмотреть, если заказчик ответит на [[Q-003]] «источник — CMS»: тогда нужен полноценный воркфлоу risk-аппрува и этот ADR заменяется новым.
