# ADR-0007 — Инструментальная обвязка M0 и принуждение границ

> [!success] Статус: ✅ accepted `2026-07-29`

## Контекст

ТЗ разд. 9 требует, чтобы модуль не импортировал внутренности другого модуля — только публичный интерфейс, и формулирует цель: возможность выделить `delivery` в отдельный сервис без переписывания. ТЗ разд. 8 требует, чтобы CI блокировал мёрж при падении любой проверки.

Соглашение «мы так не делаем» этой задачи не решает: оно держится ровно до первого срочного релиза. Нужен механизм, который ловит нарушение автоматически.

Второй вопрос: какой объём зависимостей объявлять на M0, когда приложения ещё нет.

## Решение

**1. Границы принуждаются ESLint через `no-restricted-imports` с паттернами по зонам.**

Три правила, по одному на направление зависимости:

| Зона | Запрещено | Смысл |
|---|---|---|
| любой код | `@/modules/*/**`, `@/platform/*/**` | только публичный интерфейс, не внутренности |
| `stream`, `design`, `trading` | `@/modules/delivery` | домен не знает, что его данные отдают наружу |
| `platform` | `@/modules/**` | основание не зависит от того, что на нём стоит |

**2. Сами правила покрыты тестами.** `src/platform/architecture.test.ts` прогоняет линтер по синтетическим файлам через Node API ESLint и проверяет, что нарушение действительно ловится, а разрешённый импорт — проходит. Без этого правило живёт до первого рефакторинга конфигурации: кто-то ослабит паттерн, и никто не заметит.

**3. `process.env` читается ровно в одном файле** — `src/platform/config/env.ts`. Запрет реализован правилом `no-restricted-syntax` по AST-селектору и тоже покрыт тестом.

**4. Состав зависимостей на M0 — минимальный и разрешаемый.** Сейчас объявлены только те пакеты, код на которых действительно написан: `zod`, `pino` и инструменты разработки. Payload, Next и React добавляются отдельным шагом, когда на машине появится тулчейн и дерево зависимостей можно будет реально разрешить и зафиксировать в lock-файле.

## Альтернативы

- **`dependency-cruiser`** — специализированный инструмент, выразительнее в описании графа зависимостей. Отвергнут на M0: это ещё одна зависимость, ещё один конфиг и ещё один шаг в CI ради правил, которые на текущем объёме полностью выражаются встроенным правилом ESLint. Пересмотреть, когда правил станет больше десятка или понадобится проверка транзитивных путей.
- **TypeScript project references** — разделить модули на отдельные `tsconfig` и запретить импорт на уровне компилятора. Отвергнут: даёт настоящую изоляцию, но заметно усложняет сборку и IDE-опыт на этапе, когда структура ещё может уточняться. Остаётся кандидатом на момент выделения `delivery` в отдельный сервис — тогда изоляция понадобится по-настоящему.
- **Соглашение в код-ревью** — отвергнуто по причине, описанной в контексте.
- **Объявить сразу весь целевой стек (Payload, Next, React, ajv, amqplib…)** — отвергнуто: объявлять зависимости, установку которых невозможно проверить, значит зафиксировать непроверенные версии и получить конфликт разрешения при первой же реальной установке. Зависимость добавляется тогда, когда на ней пишется код.

## Последствия

- ✅ Нарушение границы роняет CI, а не обнаруживается через полгода при попытке выделить сервис.
- ✅ Правила исполняемы и покрыты тестами — ослабление конфигурации ловится.
- ✅ Lock-файл будет содержать только реально разрешённые версии.
- ❌ `no-restricted-imports` работает по строкам импорта, а не по графу: обход через реэкспорт из чужого `index.ts` формально пройдёт. Смягчается тем, что публичный интерфейс — это и есть точка, где такой реэкспорт виден на ревью.
- ❌ Правила задаются трижды (базовое + две зоны), потому что flat-config заменяет опции правила, а не дополняет их. Общие паттерны вынесены в переменные, но дублирование остаётся и требует внимания при правках.
- 🔁 Пересмотреть при выделении `delivery` в отдельный сервис — тогда project references станут оправданы.
