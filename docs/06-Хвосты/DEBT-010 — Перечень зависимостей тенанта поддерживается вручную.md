# DEBT-010 — Перечень зависимостей тенанта поддерживается вручную

> [!warning] Карточка
> **Статус:** open · **Приоритет:** p2 · **Когда платим:** M3, до конца этапа
> **Где:** `src/platform/tenancy/dependents.ts`

## Как должно быть

Проверка «на тенанта что-то ссылается» знает обо **всех** коллекциях с обязательной связью на тенанта — потому что выводит их из конфигурации, а не хранит списком.

## Как сделано сейчас

Список задан константой. Каждая новая коллекция требует дописать в неё строку.

## Почему это уже проблема

Три раза подряд один и тот же отказ:

| Когда | Что забыли | Как проявилось |
|---|---|---|
| `2026-08-05` | `articles` | удаление сайта падало нарушением `NOT NULL` |
| `2026-08-05` | `videos`, `promos` | то же самое |
| `2026-08-06` | три коллекции токенов | то же самое |

Каждый раз ошибка находилась одинаково — падением интеграционного теста, который сносит фикстуру. То есть **защита есть, но срабатывает не там, где ошибка допущена**, и объясняет её не сразу.

> [!important] Что здесь на самом деле сломано
> Не список. Сломано то, что правило звучит как «не забудь дописать» — а такие правила не работают. Три повторения подряд это доказали.

## Чем это грозит

Само по себе ничем: обязательная связь не обнуляется, и целостность не страдает. Страдает внятность — вместо «у сайта есть материалы» человек видит сообщение про `site_id`. Ровно ради этой внятности проверка и заводилась.

## Когда платим

M3, до конца этапа.

- [ ] перечень выводится из конфигурации Payload: все коллекции, где есть обязательная связь `relationTo: 'tenants'`;
- [ ] подпись для человека остаётся настраиваемой — «материалы» читается лучше, чем `articles`;
- [ ] тест утверждает, что выведенный перечень **не пуст** и содержит известные коллекции: пустой перечень выключил бы проверку молча;
- [ ] тот же приём стоит рассмотреть для очистки фикстур в тестах — порядок сноса тоже поддерживается руками.
