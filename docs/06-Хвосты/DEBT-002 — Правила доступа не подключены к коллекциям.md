# DEBT-002 — Правила доступа не подключены к коллекциям

> [!warning] Карточка
> **Статус:** open · **Приоритет:** p1 · **Когда платим:** M0, **до появления первых данных**
> **Где:** `src/platform/tenancy/access.ts` (логика есть), `src/platform/**/**.collection.ts` (не подключена)
> **Связано:** [[ADR-0010]], [[TASK-003]]

## Как должно быть

Каждая коллекция, содержащая данные тенанта, объявляет `access.read/create/update/delete`, которые строят условие выборки из `resolveEffectiveAccess`. Пользователь вне привязки не получает чужие данные ни списком, ни по идентификатору, ни через API.

## Как сделано сейчас

Правила изоляции **реализованы и покрыты 19 тестами**, но существуют как чистая логика: ни одна коллекция их пока не вызывает. Коллекции `tenants` и `users` объявлены без `access`.

## Почему так

Порядок работ: сначала проверяемая логика, потом её подключение. Обратный порядок означал бы правила, которые невозможно протестировать без поднятой базы, — то есть на практике непроверенные.

## Чем это грозит

> [!danger] Пока данных нет — ничем. С появлением первого тенанта — это открытый доступ.
> Коллекция без `access` в Payload доступна любому аутентифицированному пользователю. То есть в момент, когда в системе появится второй тенант, редактор одного сайта сможет читать и править данные другого — прямое нарушение критерия приёмки «редактор сайта A технически не может прочитать данные сайта B».

## Когда платим

**До создания первого тенанта в любой базе, включая локальную.** Не «до релиза» и не «до прода»: локальная база с двумя тенантами и без правил доступа приучает к тому, что всё видно всем, и разрыв перестаёт быть заметным.

Критерий закрытия:
- [ ] `access` объявлен на всех коллекциях с данными тенанта;
- [ ] интеграционный тест: редактор сайта A получает 403/404 на данных сайта B — и списком, и по прямому идентификатору;
- [ ] тест на пустую привязку: пользователь без тенантов не видит ничего.
