# DEBT-002 — Правила доступа не подключены к коллекциям

> [!success] Карточка
> **Статус:** ✅ paid `2026-07-29` — до создания первого тенанта, как и было условлено
> **Решение:** [[ADR-0012]] · **Остаток:** [[TASK-009]] — проверка на живой БД

## Как должно быть

Каждая коллекция, содержащая данные тенанта, объявляет `access.read/create/update/delete`, которые строят условие выборки из `resolveEffectiveAccess`. Пользователь вне привязки не получает чужие данные ни списком, ни по идентификатору, ни через API.

## Как сделано сейчас

Правила изоляции **реализованы и покрыты 19 тестами**, но существуют как чистая логика: ни одна коллекция их пока не вызывает. Коллекции `tenants` и `users` объявлены без `access`.

## Почему так

Порядок работ: сначала проверяемая логика, потом её подключение. Обратный порядок означал бы правила, которые невозможно протестировать без поднятой базы, — то есть на практике непроверенные.

## Чем это грозит

> [!danger] Пока данных нет — ничем. С появлением первого тенанта — это открытый доступ.
> Коллекция без `access` в Payload доступна любому аутентифицированному пользователю. То есть в момент, когда в системе появится второй тенант, редактор одного сайта сможет читать и править данные другого — прямое нарушение критерия приёмки «редактор сайта A технически не может прочитать данные сайта B».

## Как погашен

`2026-07-29`, до создания первого тенанта — решение [[ADR-0012]].

- [x] `access` объявлен на обеих коллекциях: `tenants` (по полю `id`) и `users` (по полю `tenants`).
- [x] Решение о доступе переводится в условие выборки `{ поле: { in: [...] } }` — ограничение уходит в запрос к БД.
- [x] Добавлено поле привязки `tenants` у учётной записи; без привязки запись не сохраняется.
- [x] Закрыто повышение полномочий: поля `role`, `tenants`, `isActive` правит только кросс-тенантная роль, при этом человек может сменить себе пароль.
- [x] 36 новых тестов: разбор действующего лица, правила учётной записи, перевод решения в условие.

## Что осталось

Правила подключены, но проверены модульно: наши тесты покрывают **наш** перевод решения в условие, а не поведение Payload с этим условием. Доказательство пункта приёмки требует теста против работающего приложения с базой — [[TASK-009]], приоритет `p0`.

Хвост закрыт именно как хвост: разрыв «логика есть, но не подключена» устранён. Оставшееся — не упрощение, а работа, для которой нужна поднятая БД.
