# DEBT-005 — Неудачный вход не фиксируется

> [!warning] Карточка
> **Статус:** open · **Приоритет:** p1 · **Когда платим:** M1, вместе с собственной ручкой входа
> **Где:** аутентификация Payload · **Связано:** [[DEBT-004]], [[ADR-0014]]

## Как должно быть

В журнале есть `login-failed`, `access-denied` и факт блокировки учётной записи после перебора попыток. Без них невозможно увидеть подбор пароля: успешные входы видны, а сотня неудачных перед ними — нет.

## Как сделано сейчас

Не фиксируется ничего из перечисленного.

Причина установлена **фактом, а не предположением**: в типах `CollectionConfig` Payload объявляет только `beforeLogin`, `afterLogin`, `afterLogout`, `afterMe`, `afterRefresh` и `afterForgotPassword`. Хука на неудачный вход среди них нет — `beforeLogin` вызывается уже после успешной проверки пароля и служит для запрета входа, а не для его провала.

Отдельно: `afterForgotPassword` **не получает `req`**, поэтому записать из него событие нечем — нет ни экземпляра `payload`, ни транзакции.

Текущее поведение закреплено интеграционным тестом: попытка входа с неверным паролем не оставляет следа, и тест это утверждает явно. Он упадёт, когда пробел закроют.

## Почему так

Реализовать неудачный вход можно только собственной ручкой входа поверх операции Payload: перехватить отказ, записать событие, вернуть тот же ответ. Это самостоятельная работа, и делать её вместе с первой версией журнала значило бы отложить обе.

Собственная ручка входа всё равно понадобится на M1 — там же появляются ключи доставки и их скоупы.

## Чем это грозит

> [!danger] Подбор пароля не виден
> Блокировка после пяти попыток работает (ТЗ разд. 6), но **тихо**: в журнале не останется ни попыток, ни самой блокировки. При разбирательстве «была ли атака» ответить будет нечем.

Пока в системе нет настоящих учётных записей, риск отсутствует.

## Когда платим

M1, вместе с собственной ручкой входа.

- [ ] `login-failed` пишется при неверном пароле и при несуществующей почте — одинаково, чтобы по ответу нельзя было различить эти случаи;
- [ ] блокировка после перебора фиксируется отдельным событием;
- [ ] `access-denied` пишется при отказе правил доступа;
- [ ] событие содержит адрес источника запроса — иначе по нему нельзя отличить перебор от забывчивости одного человека;
- [ ] тест «неудачный вход пока НЕ фиксируется» заменён на положительный.
