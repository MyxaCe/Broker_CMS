# 2026-08-03 — События аутентификации в журнале

## Погашен [[DEBT-004]]

**Смена пароля фиксируется.** Решение оказалось в том, чтобы ставить отметку там, где значение ещё видно: в `beforeChange` пароль есть, в `afterChange` его уже нет. Отметка кладётся в контекст запроса и попадает в событие изменения; само значение не записывается.

Побочно решилась вторая половина проблемы: изменение, состоящее из одного лишь пароля, раньше выглядело как «изменений нет» и пропадало целиком. Теперь оно попадает в журнал — отдельный тест на это есть.

**Вход фиксируется** через `afterLogin`. **Выход** подключён через `afterLogout`, но — честно — **автотеста на него нет**: у локального API Payload нет операции выхода, проверить можно только по HTTP. Это единственное, что здесь заявлено без прогона.

## Что выяснилось фактом, а не рассуждением

Прежде чем реализовывать, посмотрел, какие хуки Payload вообще предоставляет. В типах `CollectionConfig` их шесть: `beforeLogin`, `afterLogin`, `afterLogout`, `afterMe`, `afterRefresh`, `afterForgotPassword`.

**Хука на неудачный вход среди них нет.** `beforeLogin` вызывается уже после успешной проверки пароля и служит для запрета входа, а не для его провала. Отдельно: `afterForgotPassword` **не получает `req`** — записать из него событие нечем, нет ни экземпляра `payload`, ни транзакции.

Заведён [[DEBT-005]]: неудачный вход и блокировка после перебора требуют собственной ручки входа, которая всё равно понадобится на M1 вместе с ключами доставки. Текущее поведение закреплено интеграционным тестом — он утверждает, что следа не остаётся, и упадёт, когда пробел закроют.

> [!danger] Почему это `p1`, а не мелочь
> Блокировка после пяти попыток работает, но **тихо**: в журнале не останется ни попыток, ни самой блокировки. Успешные входы видны, а сотня неудачных перед ними — нет. При разбирательстве «была ли атака» ответить нечем.

## Мелочь, которая стоила миграции

`logout` не было в перечне действий журнала — добавление значения в перечисление потребовало отдельной миграции. Прошла без осложнений: `ALTER TYPE ... ADD VALUE` применился в обеих базах.

**Проверки:** 261 модульный + 52 интеграционных.

## Состояние M0

Открытых хвостов приоритета `p1` в M0 не осталось: [[DEBT-005]] отнесён к M1, где для него появится подходящее место, [[DEBT-003]] — `p3`.
