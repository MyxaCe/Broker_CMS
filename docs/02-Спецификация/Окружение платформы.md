## 2. Шина событий

> [!success] Соглашение о событиях восстановлено `2026-08-03` — [[ADR-0017]]
> **Ключи маршрутизации:** `<домен>.<сущность>.<действие>.v<версия>` — например `terminal.account.opened.v1`.
> **Outbox соседнего сервиса:** `event_id` (uuid, уникальный), `routing_key`, `payload` (jsonb), `occurred_at`, `published_at`, `attempts`, `next_attempt_at`, `last_error`; частичный индекс `WHERE published_at IS NULL`.
> **Публикация:** topic-обменник, `durable`, канал с подтверждениями, `persistent`, `messageId = event_id`, `timestamp` из `occurred_at`.
>
> Письменной спецификации формата на контуре нет — соглашение восстановлено по коду. Стоит свериться с командами при первом реальном обмене.

- **vhost:** `platform` (не `/`)
- **Exchanges:** `platform.events` (topic), `platform.dlx` (topic)
- **Очереди:** `platform.dlq` (пусто), `crm.ext-test` (1 сообщение, 0 консюмеров)
- **Пользователи:** `admin`, `mds`, `terminal`, `site-web`, `crm`, **`cms`**

> [!success] Учётка `cms` уже заведена
> Права: `configure/write/read` = `^(platform\.events|cms\..*)$`. То есть CMS **может** объявлять собственные очереди с префиксом `cms.` и публиковать в `platform.events`. Отдельного запроса кредлов не требуется — в отличие от консюмера сайта, который простаивает именно из-за прав.

## 3. MDS — market data service

- `GET /health` → сейчас `degraded`, причина `budget_exhausted:twelvedata`
- `GET /v1/instruments` → **481 инструмент** (binance 467 + twelvedata 14), 106 КБ
- Форма записи: `{ symbol, name, category, segment, digits, provider, currency, icon, group, stale }`
- Провайдеры: Binance (WebSocket, живой) + TwelveData (тариф `basic`, бюджет 800 кредитов/сутки, **исчерпан**: 824/800, восстановление `2026-07-29T00:00Z`)
- Каталог собирается из `binance-exchangeInfo`, обновление вселенной раз в 60 мин

> [!warning] 481 сегодня — это снимок момента, а не проектное ограничение
> ТЗ разд. 1 указывает «инструментов во вселенной MDS: **2000+**». Фактически сейчас — 481. **Проектируем под 2000+**, как требует ТЗ: двухпанельный выбор с виртуализацией списка, массовыми операциями, поиском и фильтрами. Текущее число влияет на планирование нагрузки, но не понижает планку требований — основание [[ADR-0006]].
>
> Отдельно: MDS **штатно бывает `degraded`** из-за исчерпания бюджета внешнего провайдера. Это подтверждает требование ТЗ 4.2 — локальный снапшот обязателен, синхронные походы в MDS недопустимы.

## 4. Текущая CMS — только как источник данных для миграции

> [!danger] Код текущей CMS не переиспользуется — [[ADR-0006]]
> Broker CMS v2 пишется **с нуля, ни байта из существующего сервиса**. Решение заказчика: другая команда нашла в работающей на проде CMS **более 40 ошибок**, сервис невелик, чинить накопленное дороже и менее предсказуемо, чем построить заново по ТЗ.
> Ниже — сведения, нужные исключительно для **карты миграции данных** (ТЗ разд. 10) и для legacy-адаптера. Не для заимствования решений.

Репозиторий `/opt/site-web/Broker_CMS`. Стек: Payload `3.86.0`, Next `15.4.11`, React `19.1.0`, Postgres 16, pnpm 9.15.9.

**14 ресурсов legacy-контракта** — ровно те, о которых говорит ТЗ разд. 10; отдаются через одну ручку `/v1/cms/[...path]`:

`brand` · `navigation` · `faq` · `instruments` · `accounts` · `promotions` · `partners` · `academy` · `streams` · `contacts` · `careers` · `legal` · `system-status` · `cabinet-home`

Плюс отдельная коллекция `articles`.

**Что из этого пригодится и в каком качестве:**

| Артефакт | В каком качестве используем |
|---|---|
| Формы ответов `/v1/cms/*` | описание **legacy-контракта**, который переходный адаптер обязан воспроизвести поверх новой модели |
| Схема БД `broker_cms` | вход для скрипта импорта содержимого |
| Наполнение (`apex-ru`: 66 инструментов, 12 разделов legal, 15 вакансий, 22 пункта FAQ) | оценка объёма миграции |
| Потребители legacy-эндпоинтов (`web`, `cabinet`) | план поэтапного переезда |

> [!warning] Чего мы из старого контракта НЕ берём
> Старые JSON Schema описывают модель из **14 плоских ресурсов**. ТЗ требует принципиально другой: блочные страницы, релизы, наследование, измерения выдачи. Взять старые схемы — значит унаследовать старую модель через заднюю дверь. Канон `src/contracts/` пишется заново; старые схемы читаются только при составлении карты соответствия.

## 5. Дефекты текущего контура — как negative-требования

> [!danger] Три пункта, которые новая версия обязана исключить по конструкции
> Это не список «что починить», а список «что не должно быть возможно» — по [[ADR-0006]] ни один из дефектов не переносится.
>
> **1. Инвалидация — fire-and-forget HTTP.** `src/lib/notify-site.ts`: HMAC-подписанный POST на сайт, 3 попытки с задержкой **в памяти процесса**. Ни outbox, ни шины: в CMS нет ни одного упоминания `amqp`/`rabbit`/`outbox`. Перезапуск контейнера между попытками — событие потеряно навсегда, и об этом никто не узнает. Прямое анти-требование ТЗ разд. 13.
> Показательно, что в `Sait_Platform` паттерн outbox + relay **уже реализован** — то есть в компании он принят, просто CMS до него не дошла.
>
> **2. CMS сегодня — источник истины по торговым условиям.** `fields/Instruments.ts`: `leverageMax` типа `text` («1:500» строкой), `spreadFrom` типа `text`, `swapFree` чекбоксом; `fields/Accounts.ts`: `spreadPips`. Значения вводятся руками, не сверяются ни с чем, и уходят наружу через `GET /v1/cms/instruments` (зафиксировано в «Интеграционной спецификации CRM»). Это ровно тот регуляторный риск, который описан в [[ADR-0004]] — и он **уже действует в проде**, а не является гипотезой.
>
> **3. Нативные поверхности Payload.** GraphQL в зависимостях, `src/app/(payload)/api` присутствует. Требует проверки и отключения — [[TASK-006]].

## 6. Чего в контуре нет

| Компонент | Статус | Что делать |
|---|---|---|
| **Торговое ядро** | ❌ отсутствует | подтверждено обследованием — см. [[ADR-0005]] |
| **Redis** | ❌ нет (есть только внутренний у GlitchTip) | добавить в стек: кеш выдачи + rate limit (ТЗ разд. 9) |
| **S3-совместимое хранилище + CDN** | ❌ нет | медиа лежит в docker-volume `cms-media`; ТЗ 5.3 требует S3 + отдельный домен раздачи |
| **Vault / хранилище секретов** | ❌ нет | секреты в `deploy/.env`; ТЗ разд. 6 требует vault или envelope-шифрование |
| **Reverse-proxy, HTTPS** | ❌ нет | сервисы торчат портами наружу по HTTP; ТЗ разд. 6 требует только HTTPS за прокси и запрещает публиковать админку наружу |

> [!note] Это тестовый контур
> Часть пунктов (HTTPS, прокси) допустимы для теста, но должны быть заведены как требования к продовому контуру, а не «всплыть» при выкатке. Зафиксировано в [[Q-005]].
