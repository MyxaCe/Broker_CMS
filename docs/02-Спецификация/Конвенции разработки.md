## Уже действует

1. **Документация обновляется вместе с изменением**, по чек-листу [[Регламент документации#2. Чек-лист после каждого изменения]]. Изменение без записи не считается сделанным.
2. **Хвост в коде помечается** комментарием `// TODO(DEBT-XXX): причина` и одновременно заметкой в [[Хвосты (индекс)]]. Одностороннее упоминание запрещено — хвост должен находиться из обеих сторон.
3. **Даты — только абсолютные**, формат `YYYY-MM-DD`.
4. **Перед коммитом — `pnpm run verify`.** Он прогоняет ровно то же, что CI: линтер, формат, типы, тесты.

## Локальный контур

Инфраструктура поднимается в Docker, приложение запускается на машине — чтобы цикл «правка → тест» не проходил через сборку образа.

```bash
docker compose -f docker-compose.dev.yml up -d     # Postgres, Redis, RabbitMQ, MinIO
cp .env.example .env                                # значения уже совпадают с compose
pnpm run migrate                                    # применить миграции
```

Порты смещены относительно стандартных (Postgres `5433`, Redis `6380`, RabbitMQ `5673`): на машине может стоять своё, а молчаливый конфликт портов диагностируется хуже, чем явное отличие.

`docker compose -f docker-compose.dev.yml down -v` — остановить и стереть данные.

## Миграции схемы

> [!important] Только миграции, никогда dev-push
> `push: false` в конфигурации Payload — на **любой** БД, включая локальную (ТЗ разд. 13). Иначе схема у разработчика и в проде расходится незаметно, а миграция, которую никто не прогонял локально, впервые исполняется на бою.

```bash
pnpm run migrate:create <имя>   # создать
pnpm run migrate                # применить
pnpm run migrate:status         # что применено
```

`migrate:create` автоматически прогоняет `scripts/normalize-migrations.mjs`: генератор Payload выдаёт файл, который не проходит наши проверки — типы импортируются как значения, а в сигнатуре остаются неиспользуемые параметры. Подробно и с причиной — [[BUG-001]].

Руками сгенерированный файл править не нужно. Если после `migrate:create` линтер всё же ругается на миграцию — значит шаблон Payload изменился и скрипт перестал совпадать; это повод обновить скрипт, а не файл.

> [!important] Откат миграции нужно проверять руками
> Сгенерированный `down` не исполняется генератором и бывает нерабочим: для миграций с внешними ключами Payload ставит `DROP TABLE ... CASCADE` раньше удаления самого ключа, и откат падает ([[BUG-003]]).
> При добавлении миграции со связями: прогнать `pnpm run migrate:down`, затем `pnpm run migrate` в тестовой базе. Миграция, чей `down` не работает, — это миграция без пути назад.

> [!warning] `migrate:create` бывает интерактивным
> Если генератор не может сам решить, создана таблица или переименована, он **задаёт вопрос в терминале**. В неинтерактивной оболочке команда молча завершается, ничего не создав — и это легко принять за «изменений нет».
> Признак: команда отработала, а в `src/migrations/` не появилось файла. Запускать в обычном терминале.

> [!important] Сгенерированные типы коммитятся
> `src/payload-types.ts` создаётся командой `pnpm run generate:types` и хранится в репозитории. После изменения коллекций его нужно перегенерировать: иначе проверка типов идёт против устаревшего описания и становится декоративной.
> CI ловит расхождение отдельным шагом — перегенерирует и сравнивает с закоммиченным.

> [!danger] Имена полей могут столкнуться со служебными таблицами Payload
> Payload сам создаёт таблицы вида `<коллекция>_locales`, `_versions`, `_rels`. Поле с таким именем порождает таблицу-двойника, и **вся коллекция перестаёт читаться** — с ошибкой внутри drizzle, никак не указывающей на имя поля ([[BUG-002]]).
>
> Опасные имена: `locales`, `versions`, `rels`, `preferences`, `sessions`.
> Проверка занимает секунду: после `migrate:create` посмотреть в миграции, не совпало ли имя созданной таблицы с тем, что фреймворк создаёт сам.

## Чтения, уходящие наружу

> [!danger] `overrideAccess` указывается явно на каждом таком чтении
> В локальном API Payload умолчание — `true`: «не указать» означает **обойти все правила доступа**, а не применить их. Наш принцип обратный, и на этом расхождении черновики попали в ленту ([[BUG-005]]).
>
> Ошибка выглядит как отсутствие кода, а не как неправильный код: правило доступа написано, верно, покрыто тестами и подключено — просто вызов проходит мимо. На ревью замечать нечего.
>
> Правило: **любое чтение, результат которого уходит наружу, задаёт `overrideAccess` явно**. Служебные чтения (разрешение цепочки тенантов, публикатор outbox) обходят правила осознанно и с комментарием, почему это безопасно.

## Составные строки

> [!danger] Разделитель обязан быть вне алфавита того, что он разделяет
> Ключ доставки `bkc_<id>_<секрет>` разбирался по `split('_')`, а обе части кодировались в `base64url`, где `_` — допустимый символ. Примерно каждый пятый корректно выданный ключ отвергался как испорченный ([[BUG-004]]).
>
> Правило касается всего склеенного: ключей кеша, идентификаторов событий, составных ключей записей. Проверка — выписать алфавит каждой части и убедиться, что разделителя в нём нет; если убрать нельзя, разбирать по позиции первых разделителей, а не по всем.
>
> Тест на такое **обязан перебирать**: дефект от случайных данных проявляется не в каждом значении, и однократная проверка зеленеет через раз.

## Тесты

| Команда | Что прогоняет | Нужна ли БД |
|---|---|---|
| `pnpm run test` | модульные, вся логика без внешних систем | нет |
| `pnpm run test:integration` | поведение системы целиком, против настоящей базы | да |
| `pnpm run verify` | линтер, формат, типы, модульные тесты — то же, что CI | нет |

Модульные тесты обязаны выполняться **без окружения и за секунду**: набор, требующий поднятой инфраструктуры, перестают запускать, и он тихо перестаёт что-либо значить. Поэтому интеграционные вынесены в отдельную конфигурацию и исключены из быстрого прогона.

Интеграционные читают окружение из `.env` и `.env.test` (второй перекрывает первый — там отдельная база: тесты стирают коллекции перед прогоном). В CI файлов нет, переменные задаются в задании.

```bash
docker compose -f docker-compose.dev.yml up -d
pnpm run migrate:test          # применить миграции в тестовую базу
pnpm run test:integration
```

> [!important] Что проверяет только интеграционный набор
> [[BUG-002]] существовал с момента создания коллекции и не проявился ни в одной из 141 модульной проверки — потому что ни одна из них не обращалась к базе. Первый же интеграционный тест уронил сборку на первом шаге.

## Подлежит заполнению

- [ ] **Язык и именование** — язык кода и комментариев, именование коллекций, полей, эндпоинтов, событий.
- [ ] **Структура файлов внутри модуля** — где живут коллекции, хуки, сервисы, схемы, тесты.
- [ ] **Границы модулей** — что считается публичным интерфейсом, как это принуждается технически (eslint-правило / project references).
- [ ] **Работа со схемами** — где канон (`src/contracts/`), как генерируются типы, как обновляются фикстуры.
- [ ] **Миграции БД** — именование, порядок, откат, запрет dev-push.
- [ ] **Тесты** — структура и именование; обязательные уровни по ТЗ разд. 8: unit, контрактные, доступ, интеграционные, негативные, миграции, E2E, нагрузочные.
- [ ] **Git** — ветки, формат коммитов, требования к PR, чек-лист ревью (включая пункты документации).
- [ ] **Логи и ошибки** — формат pino-логов, обязательные поля (`request-id`, `site`, `actor`), что нельзя логировать (секреты, PII).
