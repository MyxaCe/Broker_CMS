# 🏗️ Архитектура

## 1. Незыблемые принципы (ТЗ разд. 3)

> [!danger] Приоритет над удобством реализации
> Отступление от любого пункта — только ADR с явным согласием заказчика.

1. **Fail-closed везде.** Нет ключа — 401. Нет конфигурации — процесс не стартует. Нет перевода обязательного документа — релиз не собирается. Никаких «если переменная задана, то проверим».
2. **Схема — закон на обеих границах.** Каждый ответ валидируется JSON Schema перед отправкой; каждый внешний ответ (MDS) — перед использованием. Каждое поле с `format`/`enum`/`pattern` в схеме выдачи обязано иметь эквивалентный валидатор в админке. Асимметрия «строгий выход, свободный вход» — прямая причина падений.
3. **Изоляция тенантов — правило доступа, а не фильтр интерфейса.** Пользователь вне привязки к сайту не читает его данные ни одним способом, включая прямой API.
4. **Иммутабельность опубликованного.** Только новая версия, никаких правок задним числом.
5. **Одна дверь наружу.** Единственный документированный, версионированный, валидируемый API доставки.
6. **Наблюдаемость — часть функциональности.** Недоехавшее событие обязано быть видно и повторяемо.
7. **Доказуемость.** На любой момент прошлого система отвечает: что было опубликовано, кем и когда одобрено.

## 2. Структура модулей (ТЗ разд. 9)

```
src/
├── modules/
│   ├── stream/     часть 1: новости, видео, промо, обучение, статус
│   ├── design/     часть 2: токены, блоки, страницы, навигация, SEO
│   ├── delivery/   часть 3: API, релизы, кеш, события, ключи
│   └── trading/    часть 4: тема терминала, инструменты, вотчлисты, кабинет
├── platform/       тенанты, наследование, auth, роли, воркфлоу, аудит, медиа, планировщик
└── contracts/      JSON Schema + сгенерированные типы + фикстуры (канон)
```

> [!important] Правило границ
> Один деплоймент, но модуль **не импортирует внутренности другого — только его публичный интерфейс**.
> Цель: возможность выделить `delivery` в отдельный масштабируемый сервис без переписывания.

## 3. Оси разрешения выдачи

Ключевая сквозная абстракция, от которой зависят [[Q-001]] и [[Q-002]]. Предложено в [[ADR-0003]].

Любой ответ доставки — функция от кортежа **разрешённых измерений**:

```
(site, releaseId, locale, jurisdiction, variant) → ответ
```

Все пять участвуют в ключе кеша и в `ETag`. Механизм их *разрешения* (жёстко закреплён / гео-детекция / эксперимент) может усложняться по этапам, но **форма контракта не меняется**. Это позволяет отложить гео-персонализацию и A/B на M5, не переписывая доставку.

## 4. Стек (ТЗ разд. 9)

Payload 3 (актуальная стабильная) · Next.js 15 · React 19 · Postgres 16 · S3-адаптер хранилища · Redis (кеш выдачи + rate limit) · RabbitMQ · pino · zod (окружение и внешние ответы) · ajv (контракты) · Vitest · Playwright · Docker.

Схема БД — **только миграции**; dev-push запрещён на любой БД, где есть миграции.

## 5. Анти-требования (ТЗ разд. 13)

> [!danger] Не делаем ни при каких обстоятельствах
> - свободный холст с абсолютным позиционированием;
> - произвольный CSS/HTML редактору (исключение — единственный raw-блок под ролью admin, с санитайзом и записью в аудит);
> - хранение в CMS котировок и реальных торговых условий (только витрина со ссылкой на источник истины — см. [[ADR-0004]]);
> - родной REST/GraphQL фреймворка как публичная вторая дверь к данным;
> - смешивание dev-push схемы и миграций на одной БД;
> - отдача наружу чего-либо, не прошедшего валидацию схемой;
> - состояние редактора (выбранный сайт) как единственный механизм изоляции данных;
> - fire-and-forget HTTP для инвалидации кеша;
> - создание учётных записей с предопределёнными паролями.
