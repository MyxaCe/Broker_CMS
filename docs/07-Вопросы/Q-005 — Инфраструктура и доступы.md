## Предложения по каждому пункту

> [!tip] Готовые решения, а не открытые вопросы
> Ниже — конкретные варианты с обоснованием. Если возражений нет, можно согласовать списком; менять инфраструктуру потом дороже, чем выбрать сейчас.

### 1. Обратный прокси и HTTPS → **Caddy**

Автоматические сертификаты Let's Encrypt без отдельного certbot и cron. Конфигурация на три домена умещается в десяток строк.

| Домен | Куда | Доступ |
|---|---|---|
| `api.<домен>` | приложение, **только `/v1`** | публично |
| `cms.<домен>` | админка и её служебный слой | ограничен: список адресов или VPN |
| `media.<домен>` | объектное хранилище | публично, только чтение |

Это же закрывает остаток [[TASK-006]]: периметр админки — правило прокси, а не приложения.

**Альтернатива:** nginx + certbot — привычнее, но продление сертификатов становится отдельной вещью, которая ломается молча.

### 2. Отдельный домен для медиа → **`media.<домен>`**

Требование ТЗ 5.3, и это вопрос безопасности, а не удобства: загруженный файл не должен исполняться в origin админки. Задним числом добавить нельзя — сломаются все ссылки на медиа.

Нужно только имя домена; всё остальное уже проверяется валидацией окружения.

### 3. Объектное хранилище → **MinIO на сервере** сейчас, S3 провайдера потом

Для тестового контура MinIO уже поднят в `docker-compose.dev.yml` — тот же образ ставится на VPS без изменений.

Для прода: S3-совместимое хранилище **у того же провайдера, где стоит прод** — иначе трафик медиа ходит между площадками. Конкретный выбор зависит от п. 5.

**Что нужно от вас:** только endpoint, бакет и ключи, когда контур появится.

### 4. Хранилище секретов → **файл на сервере, права `600`, вне git**

> [!danger] Зашифрованные секреты в этом репозитории — плохая идея
> Репозиторий публичный ([[Q-008]]). Даже зашифрованный файл секретов в нём — это готовый материал для офлайн-подбора, доступный всем. Поэтому вариант «SOPS в репозитории», обычно удобный, здесь отпадает.

Предложение по шагам:
1. **Сейчас:** `.env` на сервере с правами `600`, владелец — пользователь сервиса. В git не попадает (уже настроено).
2. **К прому:** секреты в менеджере — Doppler, Infisical или HashiCorp Vault. Приложение читает их при старте; `.env` исчезает совсем.

Разница между 1 и 2 — не в шифровании, а в ротации и в том, кто видел значение. Пока команда маленькая, шаг 1 честнее, чем видимость защиты.

### 5. Продовый контур → **отдельная машина, тот же Docker Compose**

Kubernetes при одном сервисе — это инфраструктура, которую придётся обслуживать вместо разработки. Compose на отдельной машине даёт то же самое и переезжает в K8s позже без переписывания приложения.

**Обязательно отдельная машина**, а не тот же VPS: тестовый контур перезапускают и ломают, и делать это на одной машине с продом нельзя.

### 6. Развёртывание → **GitHub Actions + SSH**

CI уже работает. Деплой: сборка образа в Actions, `docker compose pull && up -d` по SSH. Ключ деплоя — в секретах репозитория.

**Важно:** репозиторий публичный, поэтому воркфлоу деплоя должен запускаться **только с ветки `main` и только вручную или по тегу** — иначе внешний pull request сможет спровоцировать выкатку.

### 7. Бэкапы → **ежедневный дамп + ежемесячная проверка восстановления**

ТЗ разд. 6 требует не только бэкапов, но и **процедуры проверки восстановления**. Предложение: `pg_dump` раз в сутки в объектное хранилище, хранение 30 дней; раз в месяц — восстановление в пустую базу с прогоном интеграционных тестов против неё.

Бэкап, который ни разу не восстанавливали, — это предположение, а не бэкап.

### 8. Роли БД → **отдельная роль приложения без прав на схему**

Следствие [[ADR-0014]]: приложение не должно уметь менять схему. Миграции выполняются отдельной ролью, приложение — своей, без `CREATE`/`ALTER`/`DROP`.

Это дополнительный рубеж к триггерам неизменяемости, а не замена: триггер действует независимо от прав.
