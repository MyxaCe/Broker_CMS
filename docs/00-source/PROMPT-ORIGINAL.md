3. Незыблемые архитектурные принципы
Fail-closed везде. Нет ключа — 401. Нет конфигурации — процесс не стартует. Нет перевода обязательного документа — релиз не собирается. Никаких «если переменная задана, то проверим».
Схема — закон на обеих границах. Каждый ответ валидируется JSON Schema перед отправкой. Каждый внешний ответ (MDS) валидируется перед использованием. Каждое поле, у которого в схеме выдачи есть format/enum/pattern, обязано иметь эквивалентный валидатор в админке. Асимметрия «строгий выход, свободный вход» — прямая причина падений.
Изоляция тенантов — правило доступа, а не фильтр интерфейса. Пользователь, не привязанный к сайту, не может прочитать его данные ни одним способом, включая прямой API.
Иммутабельность опубликованного. То, что ушло наружу, нельзя изменить задним числом — только выпустить новую версию.
Одна дверь наружу. Единственный документированный, версионированный, валидируемый API доставки. Никаких «а ещё можно через родной REST фреймворка».
Наблюдаемость — часть функциональности. Событие, которое не доехало, обязано быть видно и повторяемо. Ошибка валидации контракта обязана поднять алерт, а не осесть в stdout.
Доказуемость. На любой момент времени в прошлом система обязана ответить: что было опубликовано, кем и когда одобрено.

Черновик никогда не появляется в выдаче: чтение потока всегда фильтруется по состоянию и времени публикации явным условием в запросе, а не по умолчанию ORM.

ЧАСТЬ 3 — ПЛОСКОСТЬ ДОСТАВКИ
Не «четвёртая коллекция», а сквозной слой над частями 1, 2, 4. Отвечает за: резолв тенанта → разрешение наследования → разрешение локали/юрисдикции → сборку ответа → валидацию → версионирование → кеш → инвалидацию → аутентификацию потребителей.

3.2. Модель релизов
Черновое пространство (workspace) — все правки редакторов.
Сборка релиза: валидация всего сайта → отчёт (битые ссылки, отсутствующие переводы обязательных документов, нарушения комплаенса, изображения без alt, контраст, несобранные блоки) → при чистом отчёте создаётся иммутабельный пронумерованный снапшот всей структуры сайта.
Каналы: live, staging. Канал указывает на релиз. Откат = смена указателя, секунда.
Диффы между релизами в интерфейсе: что изменилось, кем, когда.
Плановая публикация релиза на дату/время.
Наследование: публикация в родителе (бренд/регион) ставит детям задачу пересборки с показом диффа — автоматически или по подтверждению, настраивается.
Хранение: N лет (параметр), снапшот пригоден для ответа регулятору «что было на сайте в дату X».

ЧАСТЬ 4 — ТЕРМИНАЛ И ТОРГОВЫЕ СУЩНОСТИ
4.1. Тема терминала
Отдельный профиль того же графа токенов (часть 2.1), а не независимая вселенная. Наследует бренд, переопределяет специфику: цвета роста/падения, фон и сетка графика, стакан, глубина, панели, плотность интерфейса, шрифт цифр (табличные цифры обязательны). Выдаётся как JSON + CSS.
4.2. Доступ к инструментам
Локальный снапшот вселенной MDS в собственной таблице, обновляемый фоново (интервал + ручная кнопка). Админка и доставка никогда не ходят в MDS синхронно — иначе падение MDS роняет редактирование и выдачу.
Allow-list символов на сайт: двухпанельный выбор с поиском, фильтрами по группе и провайдеру, массовыми операциями, рассчитанный на 2000+ позиций.
Витринные оверрайды на символ: отображаемое имя, группа/категория витрины, порядок, бейджи (new, hot), переопределение точности, флаг «только просмотр», видимость по юрисдикции.
Реконсиляция: символы, исчезнувшие из вселенной MDS, помечаются «осиротевшими», показываются редактору, автоматически исключаются из выдачи и попадают в отчёт. Никогда не утекают потребителю.
4.3. Прочая конфигурация
Вотчлисты: именованные наборы, дефолтный для новых пользователей, наборы по вкладкам (популярное, новый листинг, растущие, объём, избранное).
Витринные торговые параметры (плечо, спред «от», swap-free, размер лота) с явным указанием источника истины. 11. КРИТЕРИИ ПРИЁМКИ
Система принята, если одновременно выполняется:
 Новый страновой сайт создаётся из шаблона за час без единой строки кода, наследуя бренд и региональные правила.
 Черновик невозможно получить через выдачу ни одним способом — доказано автотестом.
 Редактор не может опубликовать состояние, нарушающее контракт, комплаенс или доступность — сборка релиза отклоняет с внятным отчётом.
 Откат сайта на предыдущий релиз занимает секунды и подтверждён на учениях.
 На вопрос «что было опубликовано на apex-de 14 марта в 12:40 и кто это одобрил» система отвечает из интерфейса.
 Редактор сайта A технически не может прочитать или изменить данные сайта B — доказано автотестом.
 Падение MDS не мешает ни редактировать, ни отдавать контент.
 Недоставленное событие инвалидации видно в интерфейсе и повторяемо одной кнопкой.
 Ни один секрет не хранится в БД открытым текстом и не виден в UI/логах.
 Запуск с неполной конфигурацией невозможен.
 Покрытие тестами доставки, доступа и релизного цикла — полное; CI блокирует мёрж при падении.

13. АНТИ-ТРЕБОВАНИЯ (чего делать нельзя)
Не делать свободный холст с абсолютным позиционированием.
Не давать редактору произвольный CSS/HTML — кроме единственного raw-блока под ролью admin, с санитайзом и записью в аудит.
Не хранить в CMS котировки и реальные торговые условия — только витрину со ссылкой на источник истины.
Не оставлять родной REST/GraphQL фреймворка как публичную вторую дверь к данным.
Не смешивать dev-push схемы и миграции на одной БД.
Не отдавать наружу ничего, что не прошло валидацию схемой.
Не хранить состояние редактора (выбранный сайт) как единственный механизм изоляции данных.
Не полагаться на fire-and-forget HTTP для инвалидации кеша.
Не создавать учётные записи с предопределёнными паролями ни при каких обстоятельствах.
