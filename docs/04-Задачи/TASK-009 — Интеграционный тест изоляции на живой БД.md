# TASK-009 — Интеграционный тест изоляции на живой БД

> [!info] Карточка
> **Статус:** 🔵 planned · **Приоритет:** p0 · **Этап:** M0
> **Пункт ТЗ:** разд. 3, разд. 11 (критерий приёмки) · **Связано:** [[ADR-0012]]

## Описание

Правила изоляции подключены к коллекциям и покрыты модульными тестами. Но модульные тесты проверяют **наш перевод решения в условие выборки**, а не то, как Payload это условие применяет.

Критерий приёмки ТЗ сформулирован как утверждение о поведении системы: «редактор сайта A технически не может прочитать или изменить данные сайта B — доказано автотестом». Доказать это может только тест против работающего приложения с базой.

## Что проверить

Для каждой пары «редактор сайта A» / «данные сайта B»:

- [ ] выборка списком не содержит чужих записей;
- [ ] **запрос по прямому идентификатору** чужой записи возвращает отказ, а не документ — это главный сценарий, который фильтр интерфейса пропускает;
- [ ] попытка изменить чужую запись отклоняется;
- [ ] попытка удалить чужую запись отклоняется;
- [ ] то же самое через HTTP, а не только через локальный API.

Отдельно:

- [ ] пользователь с пустой привязкой не видит ничего;
- [ ] пользователь с привязкой к удалённому тенанту не видит ничего;
- [ ] отключённая учётная запись не видит ничего, даже с ролью `brand-admin`;
- [ ] привязка к бренду даёт доступ ко всем его сайтам, но не к чужому бренду;
- [ ] редактор не может изменить себе роль, привязку или флаг активности;
- [ ] редактор может сменить себе пароль.

## Зависимости

Нужен поднятый Postgres — Docker Desktop и локальный контур.

## Критерий готовности

- [ ] Тест выполняется в CI и падает при ослаблении любого из правил доступа.
- [ ] Пункт «изоляция тенантов» в [[Критерии приёмки]] отмечен со ссылкой на этот тест.

> [!danger] Почему p0
> Это не «ещё один тест», а доказательство пункта приёмки. Пока его нет, утверждение об изоляции держится на чтении кода — том самом способе проверки, от которого мы отказались.
