# TASK-008 — Чек-лист negative-требований из дефектов текущей CMS

> [!info] Карточка
> **Статус:** 🔵 planned · **Приоритет:** p1 · **Этап:** M0
> **Связано:** [[ADR-0006]], [[Окружение платформы#5. Дефекты текущего контура — как negative-требования]]

## Описание

Заказчик сообщил, что другая команда нашла в работающей на проде CMS **более 40 ошибок**, и именно это стало основанием решения о полном переписывании ([[ADR-0006]]).

Этот список — ценный материал: каждая ошибка есть доказательство того, что некоторый класс проблем **возможен** в системе такого типа. Новая архитектура обязана сделать его невозможным по конструкции, а не «учесть при разработке».

## Что сделать

- [ ] Получить перечень дефектов от заказчика.
- [ ] Классифицировать: утечка данных · нарушение изоляции тенантов · невалидная выдача · комплаенс · потеря событий · доступность · производительность · UX редактора.
- [ ] Для каждого класса сформулировать **negative-требование** — что новая система должна делать невозможным, а не просто корректно обрабатывать.
- [ ] Для каждого negative-требования указать механизм принуждения: правило доступа, схема, валидатор сборки релиза, тип в БД, ограничение в CI.
- [ ] Те, что попадают в разряд регуляторных, добавить в [[Критерии приёмки]] как проверяемые автотестом.

## Критерий готовности

- [ ] Каждый дефект из списка либо закрыт механизмом в архитектуре, либо явно помечен как неприменимый к новой модели с обоснованием.
- [ ] Ни один не остался в статусе «постараемся не повторить».

> [!warning] Почему это `p1`, а не «когда будет время»
> Три дефекта уже найдены при обследовании (fire-and-forget инвалидация, торговые условия свободным текстом, отсутствие релизной модели), и все три — архитектурные. Остальные 40+ с высокой вероятностью тоже указывают на классы проблем, а не на опечатки. Узнать их **до** проектирования модели данных дешевле, чем после.
