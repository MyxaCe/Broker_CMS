# TASK-007 — Подтвердить наличие API торгового ядра для сверки витрины

> [!failure] Карточка
> **Статус:** 🟠 in-progress · **Приоритет:** p0 (повышен) · **Этап:** M0 (запрос), реализация — M4
> **Пункт ТЗ:** 4.3 · **Связано:** [[ADR-0004]], [[ADR-0005]], [[Q-003]]

> [!danger] Обследование `2026-07-28`: торгового ядра не существует
> На тестовом контуре нет ни сервиса, ни API, ни упоминаний в документации соседних команд ([[Окружение платформы]]). Предпосылка [[ADR-0004]] **не подтвердилась**.
> Хуже: обнаружено, что **источником истины де-факто сегодня является CMS**, причём свободными текстовыми полями без сверки и аппрува — то есть регуляторный риск ТЗ 4.3 уже действует в работающем контуре.
> Приоритет повышен до `p0`. Переходный режим предложен в [[ADR-0005]] и ждёт решения заказчика.

## Описание

[[ADR-0004]] принят: источник истины по торговым условиям — торговое ядро, CMS обязана сверять витрину с ним и блокировать релиз при расхождении. Механизм сверки нереализуем, если ядро не отдаёт актуальные значения.

Задача заводится **на M0, хотя реализация на M4** — потому что если API не существует, его разработка попадает в план другой команды, и узнать об этом на M4 означает сдвинуть весь этап.

## Что нужно выяснить

- [ ] Есть ли эндпоинт, отдающий по символу/группе/типу счёта: **плечо**, **спред**, **swap-free**, **размер лота**.
- [ ] Аутентификация, лимиты, частота допустимого опроса.
- [ ] Гарантии актуальности: как быстро изменение условий в ядре становится видно через API.
- [ ] Как в ядре адресуется параметр — что станет значением `sourceRef`.
- [ ] Для агрегатов («спред от»): отдаёт ли ядро агрегат само, или CMS должна считать минимум по окну. От этого зависит поле `rule`.
- [ ] Кто владелец ядра и его дорожной карты.

## Критерий готовности

- [ ] Получен письменный ответ от владельцев торгового ядра.
- [ ] Если API есть — контракт задокументирован, поля `sourceRef` / `rule` / `tolerance` спроектированы под него.
- [ ] Если API нет — заведена внешняя зависимость с датой, [[ADR-0004]] дополнен разделом о временном режиме, и явно зафиксировано, что до появления API витринные торговые параметры **не публикуются**, а не публикуются «без сверки».

> [!danger] Почему нельзя «пока без сверки»
> Витрина без сверки — это ровно тот регуляторный риск, который ТЗ 4.3 называет прямым. Отсутствие механизма сверки не может быть закрыто хвостом со статусом `open` — только отсутствием публикации параметров.

## Лог

- `2026-07-28` — обследование VPS: **ядра нет**, CMS де-факто источник истины через свободные текстовые поля `leverageMax` / `spreadFrom` / `swapFree` / `spreadPips`. Приоритет `p1` → `p0`. Заведён [[ADR-0005]] с переходным режимом. Остаётся выяснить у владельцев ядра горизонт разработки.
